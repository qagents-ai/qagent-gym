# Where QAgents and Gym fit

Research date: **2026-11-13**. This is a private working comparison, not a performance benchmark or a release announcement. QAgents' inspected package version is **0.2.0**; Effects 0.3 and its planned crash harness are unfinished.

QAgents offers an explicit Python agent runtime with typed tools, journaled sessions and leased background execution. Gym adds persistent playbooks, scoped memory and frozen evaluation around that runtime, and can also invoke supplied LangGraph and DSPy programs. This combination is useful when the application needs inspectable execution and learning records. Its superiority over another framework has not been measured.

## What is actually available

“Implemented” below means present in the inspected source. “Demonstrated” means exercised by the repository's documented tests or examples. A scripted example checks integration behavior; it does not establish real-model quality, generalization or production reliability.

| Area | QAgents / Gym now | Demonstrated distinction and remaining limit |
| --- | --- | --- |
| Agent execution | QAgents exposes its agent loop, typed tools, prompts, hooks, testing models and provider adapters, including QCloud. `pyproject.toml` declares only `httpx` and `pydantic` as direct core dependencies. | The dependency declaration and explicit APIs are inspectable properties. Installed footprint, startup time and speed relative to other packages are unmeasured; optional integrations add dependencies. |
| Background recovery | `AgentRuntime` journals an accepted run before returning, maintains session leases and can recover eligible open runs. SQLite supports one host; Postgres supports workers on multiple hosts. | Lease acquisition tokens fence journal writes. They do not fence an external service. Paused approvals require explicit resume; shutdown preserves resumable work, while cancellation closes the run. |
| Tool outcomes | Recorded tool results are reused. An interrupted call without a result is retried only for tools declared read-only or idempotent; other outcomes are reported as unknown. | This gives the application a concrete recovery contract. Duplicate remote writes remain possible without downstream deduplication. A process crash can also repeat an in-flight model request and its cost. |
| Context learning | Gym runs generator → evaluator → reflector → curator; SQLite stores immutable episodes, memories and validated, idempotent playbook deltas with provenance. Evaluators may supply peer or user feedback. | Offline examples reuse learned rules on different tasks. The loop is ACE-inspired, not an official ACE package integration, replicated ACE benchmark or implemented social-learning algorithm. Model weights stay unchanged. |
| Evaluation | Gym captures evaluation contexts before generation and avoids learning writes during evaluation. Mem0 can supply an explicit frozen query snapshot. Episode records are still written. | These boundaries are tested. They do not freeze arbitrary external state inside an injected graph, DSPy program, tool or remote service. |
| Framework interoperability | Native LangGraph and DSPy contracts are exercised; Mem0 validates namespace/provenance. Inspect datasets, GEPA reflection data, Lightning reward payloads and metadata-only OpenTelemetry wrappers are available. | A generator adapter is not checkpoint resumption. An export or reward payload is not an executed optimizer, Inspect solver or RL training run. See [framework contracts](integrations-memory-frameworks.md), [exports](optimization.md), [tracing](integrations-tracing.md) and [RL boundary](rl.md). |
| Application workflows | The Erasmus+, banking and English/Greek voice examples execute actual QAgents policies and check application invariants. | Erasmus+ remains a fictional draft; the bank uses TEST units; the voice timings exclude live-model/network and recording/playback time. These are reproducible scenarios, not competitive benchmarks. See [Erasmus+](erasmus-example.md), [banking](banking-example.md) and [voice](voice-example.md). |

QAgents source evidence: `pyproject.toml`, `src/qagents/runtime.py`, `docs/concepts/sessions.md`, `docs/design.md`, `docs/integrations/acp.md` and `docs/integrations/devvi.md` in the inspected QAgents checkout. Gym source evidence in its checkout: `src/qagent_gym/gym.py`, `src/qagent_gym/storage.py`, `src/qagent_gym/records.py` and the linked example/validation guides.

## What the other frameworks already offer

These are capabilities documented by their maintainers, not results of a local comparison. Framework versions, persistence backends and configuration change the relevant guarantees.

| Framework | Current documented capability | Implication for QAgents positioning |
| --- | --- | --- |
| LangGraph | Checkpoints, task result reuse, interrupts and recovery; its Functional API wraps ordinary functions using entrypoints/tasks, so applications need not express every workflow as a graph. [Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api) | Neither recovery nor ordinary Python control flow is exclusive to QAgents. Compare implementation complexity and failure behavior for the same application. |
| LangGraph | Retry boundaries and idempotency guidance explicitly distinguish persisted state from external effects, including missing acknowledgements. Node timeouts/error handlers require `langgraph>=1.2`. [Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance) | QAgents' unknown-outcome policy is a meaningful contract to test, not evidence that LangGraph ignores effect safety. Match checkpoint durability and task boundaries in any benchmark. |
| CrewAI | Versioned documentation currently resolves to v1.15.41. Crews, flows and agents can checkpoint and restore, skip completed tasks and fork execution. JSON and SQLite providers are documented. Automatic checkpoint failures are logged and execution continues; manual checkpoint failures raise. [Checkpointing](https://docs.crewai.com/en/concepts/checkpointing) | Describing CrewAI as lacking persistence would be incorrect. Compare required checkpoint failure handling and restoration boundaries, rather than reducing it to role prompts. |
| PydanticAI | Current documentation lists nine durable execution engines plus a backend builder. `StepPersistence` separately supports settled-step snapshots for save/resume/fork. Engines differ in tool coverage and streaming support. [Durable execution](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) | QAgents integrates its own SQL-backed runtime; PydanticAI offers multiple engine choices. This is an architectural choice, not evidence of better recovery. |
| DSPy | GEPA optimizes program instructions using evaluation feedback; MIPROv2 searches instructions and few-shot examples. BootstrapFinetune supports a distinct weight-training path through compatible LM providers. [GEPA](https://dspy.ai/current/getting-started/gepa-optimization/), [MIPROv2](https://dspy.ai/current/api/optimizers/MIPROv2/), [BootstrapFinetune](https://dspy.ai/current/api/optimizers/BootstrapFinetune/) | DSPy supplies optimization machinery that Gym does not currently execute. Gym's explicit episode/playbook records can complement it; context updates must not be described as fine-tuning or RL. |

For an application already using QAgents, Gym adds learning/evaluation without replacing its execution loop. Existing LangGraph applications can keep their graph and checkpoint model. CrewAI is worth considering where crews and flows match the application's organization. PydanticAI is worth evaluating when one of its durable engines is already deployed. DSPy is a direct candidate when optimizing an LM program is the main objective. These are fit-based inferences from the documented interfaces, not ranked recommendations.

## Evidence that still needs to be collected

- **Cross-framework performance:** no matched measurements of latency, memory use, dependency footprint, throughput or development effort have been run. Test counts are not a substitute.
- **Real-model learning:** scripted scores demonstrate rule reuse by the scripted policies. They do not establish improvements from ACE-style reflection, Mem0 retrieval, peer correction or DSPy optimization on an unseen real workload.
- **Effects and crash behavior:** the planned Effects 0.3 work and dedicated crash harness remain open. Existing session/runtime tests do not complete that roadmap or establish that duplicate remote writes are prevented.
- **Concurrent learning and transactions:** Gym expects external serialization per namespace. Distinct updates to the same bullet can overwrite earlier text. Learning is not one atomic transaction across model execution, local adaptation and remote memory.
- **Integration breadth:** native contract checks cover the exact recorded SDK versions, not every release or hosted deployment. Gym's LangGraph adapter starts fresh threads and reports pauses; it does not resume them. QAgents' generic ACP client is verified against Devvi fixtures, not every ACP agent.

The current native framework checks used LangGraph **1.2.21**, `langchain-core` **1.8.0**, DSPy **3.5.0** and Mem0 **2.2.1**. These versions identify the tested contracts, not a claim about which package release is newest. See [the integration guide](integrations-memory-frameworks.md).

## Four prioritized experiments

These are proposed next work, not shipped capabilities. Each should produce a small reproducible artifact and a decision before expanding scope.

| Priority | Experiment | Concrete implementation and measurement | Decision criterion |
| --- | --- | --- | --- |
| 1 | Finish the Effects crash matrix | Use one local fake service with a durable operation ledger. Kill the worker before a side effect, after service commit but before acknowledgement, after result persistence, during lease takeover and during cancellation. Include a service that honors idempotency keys and one that does not. Record duplicate effects, lost accepted work, unknown outcomes and recovery traces. | Every case matches the declared contract. Missing acknowledgements remain unknown until reconciled. A local journal alone cannot establish that remote writes are deduplicated. |
| 2 | Run a matched recovery benchmark | Implement the same deterministic tool workflow in QAgents, LangGraph, CrewAI and one selected PydanticAI durable backend. Pin versions, hardware, storage durability, task boundaries and retries. Use identical fault points and inputs; then measure idle/startup memory, cold/warm latency and recovery time alongside correctness. | Compare only configurations that satisfy the same recovery requirements. Report tradeoffs and failed cases; do not declare a winner from the fastest configuration with weaker persistence. |
| 3 | Measure whether memory and correction help | Fix separate training, validation and untouched test tasks. Compare plain QAgents, Gym playbooks, playbooks plus Mem0, and DSPy GEPA under the same model/call/token budget. Start with evidence-grounded proposal sections or bilingual support answers. Include conflicting/stale memories and bad peer feedback. Store dataset versions, context snapshots and multiple seeded runs. | Adopt an approach only if heldout task quality improves without unacceptable cost or factual regressions. Use validation for selection; inspect the final test set once after choices are fixed. |
| 4 | Execute one bounded training experiment | After the previous experiment yields reliable rewards, connect an actual trainer to a small permitted model and narrow tool task. Keep SFT, prompt optimization and RL as separate baselines; persist dataset provenance, reward definition, seeds, trainer configuration, checkpoint IDs and learning curves. The existing Lightning payload is only the starting interface. | A real saved weight checkpoint must be evaluated against the frozen base model and context-only baseline. Stop if rewards are exploitable or gains do not survive heldout evaluation. No training gain should be claimed from successful payload delivery. |

Useful extensions suggested by these experiments are explicit memory-conflict review and rollback, resumable cross-framework task identities, and an operator view of pending/unknown effects. Their APIs should follow the observed failure cases. Adding more adapters before these boundaries are measured would expand compatibility work without answering whether the system is more reliable or more useful.
